CORPUS HUB V2: ASK THE QUESTION,
GET THE ONE PACK THAT ANSWERS IT

XERJ ENGINEERING · PUBLISHED 2026-10-19

When we opened the Corpus Hub on 2026-10-01, using a corpus took four commands and an index build on your own CPU. Hub v2 removes all of that. You type xerj "how does lz4 decompress a block" and the CLI picks the lz4 corpus from a signed catalogue, downloads its pre-indexed 4.4 MB pack from GitHub Releases, and answers on a node running on your machine. In four cold runs on 2026-10-19 the first question took 1.7 to 2.3 seconds from an empty cache with no node running. Repeats came back in 37 to 57 ms. The hub site changed as well. Contributors have their own pages, agent scores sit apart from human stars, every corpus page shows traffic, and agents' field reports now arrive as pull requests. Below, each change comes with a command or a URL you can check yourself.

01 · ASK

Ask without naming a corpus

The launch post closed on a promise: "the pre-indexed half — a corpus you mount instead of indexing". Hub v2 is that half. CI builds each pack, indexes it, signs it and attaches it to a GitHub Release. Your machine restores the indices as they are, without cloning a repository or running an indexer. 02 · ROUTING

Ambiguous questions come back as a choice

The router does not guess between two plausible corpora. Ask about two compressors in one sentence and it hands the decision back to you:

$ xerj "lz4 or snappy decompression speed"
more than one corpus matches; re-run with --corpus <slug>
lz4 — an agent needing fast block compression queries this for the block format and decoder loop
snappy — an agent needing cheap compression queries this for the format and the reference encoder decisions
$ echo $?
4

Exit 4 is the code xerj autoindex already uses for "needs a decision", so a wrapper script can treat it as a question to put to the user, not as an error. If no corpus clears the bar, the CLI exits 1 and names the nearest ones:

$ xerj "how do I run a github actions workflow locally"
no hub corpus matches; see xerj.org/llms.txt
closest corpora: act, astro, agentops; re-run with --corpus <slug> to ask one of them

We are keeping that example in because it is a miss. The act corpus exists for this exact question, and the router ranked it first but not confidently enough to answer. The hint was right and the verdict was wrong. That threshold is ours to fix.

There is also a third outcome that used to hide inside exit 1. Suppose hub.xerj.org is unreachable, or serves an HTML page where the signed catalogue should be, or you pass --offline with nothing cached. In rc.97 all three exit 1, the same code as "no corpus matches". An agent that scripts on exit codes reads that as "the hub has no answer" and falls back to memory. A fresh-user run on 2026-10-19 hit exactly that (#1904), and PR #1905, merged to main the same day, gives the case its own code:

exitmeaning
0answered, at least one hit
1no match, or nothing to answer from (closest corpora are named)
2usage error or unknown --corpus
3a pulled pack failed SHA-256, signature or format verification
4ambiguous: candidates printed, re-run with --corpus <slug>
5this build has no hub public key, so nothing is downloaded
6the hub catalogue cannot be loaded (on main since #1905; rc.97 still exits 1)
03 · CONTRIBUTORS

Contributor pages

Every corpus is somebody's work, so every contributor now has a page. hub.xerj.org/contributors/ lists 3,663 developers whose repositories are included with their permission, under each repository's own licence, sorted by the GitHub stars on those repositories. A profile shows exactly what was selected. Take Kayvan Sylvan's: a contributor since 2026-10-05, with one selected commit to danielmiessler/Fabric (aa3e1727b7, "fix: correct SSE streaming behavior and restore native Azure routing"). That commit is 29 files and 1,055 lines of Go and appears in 2 corpora. The repository has 44,351 GitHub stars, and the profile has 0 hub stars so far.

The page also tells you what you cannot do yet. Those corpora are still in licence review, and the card says so in plain words: "Not installable yet ... It becomes installable when this card says live in the hub." Each profile carries a README badge at /contributors/<login>/badge.svg, and the removal route is printed under it: reply to the permission email or open an issue.

04 · SIGNALS

Human stars and agent scores, kept apart

A corpus page now carries two signals, and we do not blend them. Hub stars are people clicking a star. The agent score comes from structured reviews that agents send after using a corpus, through xerj hub pull, MCP queries or the xerj_corpus_feedback tool. A review rates usefulness from 1 to 5, says whether the answer was found (yes, partial or no) and how fresh the corpus felt. It can also name a coverage gap or flag a problem: error, slow, stale or wrong. The rules are printed on every corpus page:

  • The score is a Bayesian mean of usefulness with a prior of 3.0 at weight 5. A handful of glowing reviews cannot lift a corpus far.
  • One voice per installation, per corpus, per week. Reviewers with abnormal volume are dropped.
  • A coverage gap is shown only once 3 or more agents report the same one.

The raw numbers sit behind a public endpoint. Here is act tonight, trimmed:

$ curl -s "https://hub.xerj.org/api/corpus-feedback?corpus=act"
{"ok":true,"enabled":true,"corpus":"act","reviews":0,"score":null,"confidence":"none",
 "prior":{"mean":3,"weight":5},"found":{"yes":0,"partial":0,"no":0,"rate":null},

Zero reviews and a null score. That is the true state, and the page shows it as empty instead of inventing a starting rating.

05 · TRAFFIC

Traffic and usage on every corpus page

Each corpus page has a traffic panel modelled on GitHub's, covering the last 14 days in UTC. It counts views and unique views (crawlers excluded, uniques by a hash salted with the day), pulls, hosted-hub searches, requests per agent family, and referring sites once a site has sent 3 views. Pulls are the growth in the GitHub Release download count for that corpus's pack, which includes our own verification downloads. Like the scores, it is a plain JSON call:

$ curl -s "https://hub.xerj.org/api/hub-traffic?corpus=act"
{..."totals":{"views":6,"unique_views":6,"pulls":1,"pulls_unique":null,"searches":0},
 "pulls_since":"2026-10-20","recording_since":"2026-10-19",
 "agents":[{"family":"curl","count":6}],"referrers":[]}

Six views, all from curl, and a fair share of them were us writing this post. Recording began on 2026-10-19, so every corpus starts close to zero.

Underneath sits agent usage: requests over 7 and 30 days, agent families, top topics and the most common query templates. A template replaces identifiers, versions, paths, numbers and quoted text with placeholders. It is shown only after it has been seen 3 times in 30 days, and raw queries are never published. Only requests to the hosted hub API (hub.xerj.org/api/v1/code and /def) are counted. A question answered on your own node never leaves your machine, so nothing from xerj ask with a cached pack shows up here.

06 · SIGN IN

Sign in with GitHub or Hugging Face

You can see everything above without an account. Signing in through /auth/github/login or /auth/hf/login (standard OAuth, with PKCE on both) opens the detail behind it. A corpus page adds its pack build and pin history, the full source pins and review records, and how its packs are signed. A contributor page adds every selected commit in full, with commit date, folders, review state and pin. Usage detail needs a session too; until you have one, the usage API answers "detail_requires_signin":true.

07 · FIELD REPORTS

Field reports that turn into fixes

After an agent installs or uses XERJ, the CLI now sends a short field report on its own: what the agent pointed XERJ at, what it used it for, and its verdict. The report goes out as a GitHub pull request adding one Markdown file under user-feedback/16-agent-field-reports/, forking first when the account cannot push. Only when GitHub is unavailable does it fall back to POST https://xerj.org/api/field-report, and those reports arrive as issues. --disable-feedback or XERJ_DISABLE_FEEDBACK=true turns it off. Should an agent send one without asking its user first? That is under debate in #1896, and the opt-out works whichever way that goes.

As of tonight main holds 40 reports in that folder, and 12 more came in through the API fallback as issues titled "Agent field report (API)". Here is one full loop. Several reports flagged a stray backslash in the MCP registration text that xerj init prints. Issue #1838 was opened from those reports on 2026-10-19, and PR #1848 fixed the three format strings and closed it at 23:34 UTC the same day. It is a small bug. We still care about the turnaround, because an agent has no other way to tell us the CLI printed something odd.

08 · HOW IT WORKS

How it works

The catalogue. hub.xerj.org/api/v1/catalogue.json is one JSON file, signed with a detached ed25519 signature in catalogue.json.sig beside it. The CLI fetches it with If-None-Match and checks the signature before the new bytes may replace its cache. On any network or verification failure it keeps the last good copy. Each entry holds the slug, domain, topics, a one-sentence ask_for, dependency_names, the licence (SPDX plus class), the pin SHA and date, the pack URL, size, SHA-256 and signature URL, and a term_sketch.

Routing. The router reads only that metadata, plus two things on your disk: the dependency names in your project's Cargo.lock, package.json or go.mod, and the packs you already have cached. The term sketch is a Bloom filter over the corpus's terms, built with 7 hashes. A Bloom filter can answer "possibly present" or "certainly absent" and never gives a false negative, so if the sketch rules out a word in your question, that corpus drops out without a download. A declared dependency is the strongest evidence a corpus can earn. Corpora whose licence class is excluded are removed before routing starts, which means they are never picked, never listed as a candidate and never named as closest.

The pack. A confident pick downloads that one pack from GitHub Releases, checks its SHA-256 and signature (a failure is exit 3), and restores its pre-built indices into a node. If nothing answers on localhost:9200, the CLI starts its own node on port 9300, and xerj hub stop stops that process and no other. The search itself runs on that node. The hub serves the catalogue, the web pages and a few small JSON APIs. The CLI does have a hosted switch (xerj hub config hosted on|off|auto), but no hosted client ships in the CLI yet (we checked rc.97 and main on 2026-10-19), so today every xerj ask answer is computed on your machine.

09 · GETTING STARTED

Getting started

Install the CLI, then ask. The first question starts the node and pulls the pack, and the later ones answer from the cache:

$ curl -fsSL https://xerj.org/get | sh
$ export PATH="$HOME/.local/bin:$PATH"
$ xerj "how does lz4 decompress a block"
$ xerj ask --def LZ4_compress_fast
$ xerj ask --corpus snappy "how does snappy find matches"
$ xerj hub status
$ xerj hub stop

xerj hub status lists cached packs with their age and size, plus the node, the hosted setting and the catalogue age. Add --offline to stay on cached packs, --no-fetch to forbid downloads, and --json when an agent is parsing the answer.
